# 产品说明

## 产品问题与用户

SignalDeck 为个人操作者提供一个可信的单用户 LLM agent 流水线运行器。操作者用 YAML 组织多个 agent、工具和 HTTP 操作，手动或按计划启动工作流，并在运行结束后检查实际输入、输出、失败和资源使用证据，而不是只看到一个最终文本。

当前交付目的为本地开发调试和个人使用：工作流包、调度、模型连接、运行证据以及模板/报告应能在本地内网中被快速编辑、启动、观察和复现。

## 范围与非目标

当前产品面包括：

- Workflow Package 的 YAML 导入、编辑、校验、导出、预检和启动；
- 包内 inputs、agents、output schemas、capability profiles、私有 MCP 配置、HTTP operation 节点和 workflow graph；
- 全局 Model Connections；
- Scheduled Tasks 及其预览、run-now、重叠/错过策略和 fire history；
- Runs 的队列、执行、取消、删除、重跑、不可变快照和逐步证据；
- Templates 与 Reports 的创建、编译、上传、编辑、下载和删除；
- 静态安装的 `signaldeck.finance` 与 `signaldeck.digital_oracle` 扩展贡献的 API、工具和 provider。

以下不属于当前产品面，除非项目被明确重新划定范围：公共登录、多用户认证、RBAC、组织和租户、插件市场、live broker execution、portfolio accounting、workflow memory、run fork、Studio、Tryout、orchestration、runtime-v2、simulations 和 backtests。

## 核心用户流程

1. 操作者启动本地/演示组合栈，打开浏览器界面。
2. 在 Model Connections 中配置模型提供商；API key 只写入，读取时只显示安全状态。
3. 导入、编写或选择一个 Workflow Package，完成 manifest 解析、语义校验和 preflight。
4. 手动启动运行，或创建带 IANA 时区和结构化 recurrence 的 Scheduled Task。
5. scheduler 将运行置为 queued、领取并执行包快照；每个步骤、agent 调用和 HTTP 操作写入 evidence。
6. 操作者在 Runs 中查看进度、输入、包来源、失败分类、重试、token 用量和最终输出，必要时从冻结快照创建带新 root parameters 的 rerun。
7. 需要时使用模板编译生成 markdown Report，随后编辑、过滤或下载报告。

## 功能需求

### Workflow Package

包清单使用 `signaldeck.workflowPackage/v1` YAML。包是唯一的可执行工作流 authoring root；它通过稳定的 Model Connection key 引用全局模型，通过 owner-qualified tool key 引用运行时工具。工作流节点支持 `step`、`http`、`sequence`、`fanout` 和 `loop`。

parser 必须拒绝 YAML alias、anchor、merge key、不支持的 tag、非有限数字、重复 key、重复本地 ref、raw database id、secret-like manifest field、`spec.skills`、开放对象 schema 关键字和未知 manifest 字段。secret reference 只允许出现在 HTTP request 字段。compiler 输出必须确定、可哈希，并且不泄露 secret。

包导出、manifest read 和 run provenance 不能包含私有 MCP 的 secret-bearing `env`、`headers`、`query`、raw secret、database id、run history 或 secret binding 行；Secret Bindings 只显示 key、存在性和时间戳。

### Runs 与 Scheduled Tasks

launch 和 scheduled fire 产生 queued run，并捕获 immutable package snapshot 及已解析的非 secret Model Connection runtime profile。运行状态包括 `queued`、`running`、`succeeded`、`failed` 和 `cancelled`。取消 queued run 立即生效，running run 在步骤边界协作停止。删除 schedule 会停止未来自动化并删除 schedule-owned fire，但保留现有 run 的 run-owned schedule provenance；删除 Workflow Package 会删除其拥有的 runs。

Scheduled Task 使用 `interval`、`daily`、`weekly` 或 `monthly` recurrence 和 IANA timezone，支持 overlap、misfire、JSON input template、preview、run-now 和 fire history。模板可使用 `schedule`、`fire`、`window`、`lastRun`、`vars` placeholders；渲染后必须按包 workflow input schema 校验。

### Model Connections、Tools、Templates 与 Reports

Model Connection 保存 provider/model identity、endpoint/model 设置、`protocolProfile`、超时、reasoning effort 和加密 API key。`/api/tools` 只读返回静态扩展声明的工具元数据；包通过本地 capability profile 授予工具，未知 native tool 不得静默回退为 MCP。

Templates 支持 markdown、`{{placeholders}}`、runtime inputs、compile preview、保存模板和生成报告。Reports 是按唯一 slug 保存的 markdown 快照，来源可以是 `compiled`、`uploaded`、`external` 或 `agent`；JSON Schema 的 `title` 与 `description` 仅用于显示。

## 可观察验收

当前本地交付至少应能观察到以下结果：

- `./start.sh` 能构建并启动本地/演示组合栈，浏览器可访问 `http://localhost:${APP_PORT:-8080}`，`/health` 和 `/ready` 反映服务与数据库状态；
- 两个预置 demo package 能被发现并可在配置有效 Model Connection 后启动；
- 一次运行从 queued 进入终态，并能在 Runs 中查看包快照、步骤证据、agent/HTTP 调用结果、错误或最终输出；
- Scheduled Task 的预览、保存和 run-now 不绕过 workflow input 校验，schedule 删除后历史 run 仍能读取 provenance；
- 模板和报告可以完成至少一个编译、保存、读取、编辑或下载闭环；
- 受影响代码能够通过 [`CONTRIBUTING.md`](../CONTRIBUTING.md) 和 [`开发规范.md`](开发规范.md) 指定的适用检查。

## 约束与重新评估

当前假设是单一操作者在本地内网使用，不把根目录组合镜像作为生产制品。产品便利性可以优先于额外的安全加固，但不能取消 secret 保护、数据完整性、包解析安全和现有质量检查。

当出现公网暴露、生产部署、外部用户、真实或不可丢弃数据、性能/容量验收、明确兼容承诺或新的权限/隐私要求时，重新评估产品范围、验收和架构边界。
