# 架构说明

## 系统边界

SignalDeck 是一个由浏览器前端、FastAPI backend、PostgreSQL 和外部 provider 组成的单用户系统。浏览器通过同源或配置的 API base URL 调用 backend；backend 负责 HTTP API、schema/manifest 处理、数据库访问、运行调度和外部 LLM、市场数据、HTTP、MCP provider 的调用。

当前部署边界是个人使用的本地内网。根目录组合栈是本地/演示拓扑；受支持的拆分制品是 backend、scheduler 和 frontend 镜像，生产示例位于 `docker/compose.production.example.yml`。root image 不得被当成生产制品。

外部依赖包括 PostgreSQL/pgvector、LLM provider、finance/data provider、被 Workflow Package 声明的 HTTP endpoint 和可选 MCP server。外部响应属于不可信输入，必须经过现有 parser、schema、runtime tool 和 redaction 边界。

## 组件与职责

### 前端

`frontend/` 是 React 19 + Vite 应用，使用 React Router、TanStack Query、shadcn/Radix primitives 和语义化 Tailwind token。`src/routes.ts` 声明 dashboard、Workflow Packages、Scheduled Tasks、Model Connections、Runs、Templates 和 Reports 路由。feature page 拥有领域文案、路由参数、hooks、mutation、toast、导航和校验；共享组件保持 presentational。

`src/lib/api-client.ts` 区分 `/api/v1` 扩展面和 `/api` platform 面，统一处理 JSON、文本、下载、token 重试和安全错误详情过滤。查询 key 由 `src/lib/query-keys.ts` 统一管理。

### FastAPI 入口与 API 层

`backend/app/main.py` 创建 FastAPI 应用、Logfire instrumentation、CORS、可选 `BearerTokenMiddleware`、错误 envelope、`/health` 和 `/ready`。`/ready` 通过 PostgreSQL `SELECT 1` 判断就绪。

`backend/app/api/platform_router.py` 将平台面挂载在 `/api`，包含 Workflow Packages、Schedules、Model Connections、Tools 和 Runs。`backend/app/api/router.py` 将静态扩展 API 挂载在 `/api/v1`；当前 finance 扩展提供 Templates 和 Reports 路由。

外部 JSON 使用 camelCase，backend 内部使用 snake_case；`CamelModel` 和 schema 层负责别名及请求校验。API-owned errors 使用 `{code, message, details[]}`，错误详情在 backend 和前端读取边界都进行安全过滤。

### 服务与运行时

`backend/app/services/` 负责 manifest parser/compiler/preflight、output schema compiler、Model Connection resolution、RunService、queue、scheduler materialization、agent execution、HTTP operation execution、rerun 和 read projection。`RunService` 是 launch、snapshot、execution、projection 和 rerun 的组合入口；`RunQueueService` 负责领取、lease、heartbeat 和 stale lease recovery。

`backend/app/workers/run_scheduler.py` 先物化到期 Scheduled Task，再领取 queued run，按最大并发和每包并发执行。scheduler 通过 PostgreSQL advisory lock 保证同一数据库内只有一个 worker 主循环；运行 lease 和 heartbeat 使 stale run 能恢复。

### 扩展组合根

`backend/app/extensions/registry.py` 静态声明 `INSTALLED_EXTENSIONS`。`Extension` 可以贡献 API router、server-declared tool、runtime executor、provider factory、runtime dependency surface 和 package-private MCP tool owner。当前固定扩展为：

- `signaldeck.finance`：Templates/Reports API、finance providers、market/news/sentiment/report runtime tools；
- `signaldeck.digital_oracle`：prediction market、SEC、macro/rates、crypto derivatives、CFTC 和 options 等 runtime tools，不增加 API 或导航路由。

扩展通过静态 Python wiring 注册，不使用动态 import discovery、运行时安装或 marketplace。

### 持久化层

`backend/app/models/` 定义 SQLAlchemy model，`repositories/` 提供数据访问，`db/` 负责 engine、`create_all`、seed、数据库验证和启动恢复。具体表和字段责任以 [`data-model.md`](data-model.md) 为准。

工作流包保存当前 manifest source、compiled plan、hash 和依赖面；包内 agent、output schema、capability profile、私有 MCP、HTTP operation 和 workflow graph 保持在包 artifact 中。launch 时复制 executable package snapshot 到 run-owned 表，运行随后只从冻结快照执行。

## 主要数据流

1. 前端提交 YAML 或 package 编辑内容到 `/api/workflow-packages`。
2. parser 先检查 YAML source safety 和字段形状，再执行 graph semantic validation；compiler 生成排序稳定、可哈希的 compiled plan；preflight 投影 validation、launch metadata 或 strict readiness 结果。
3. launch 验证输入、解析 Model Connection 和 extension/tool dependencies，创建 queued run、planned step/invocation rows 和 immutable package snapshot。
4. scheduler 领取 run，按 plan 运行 agent 与 HTTP operation；每一步提交状态、输入来源、输出、token、错误和可选 trace/span id。
5. read projection 将数据库状态转换为 API 的 list/detail/provenance 结构；secret-bearing 字段在存储读取、导出、日志和诊断边界被排除或脱敏。
6. Scheduled Task 由 materializer 将符合 recurrence、timezone、overlap 和 misfire 规则的 fire 转换为普通 queued run；schedule 删除后，run 保留自己的 provenance。

## 依赖方向

依赖方向保持为：

```text
浏览器页面/feature hooks
        ↓
前端 API client 与类型
        ↓ HTTP
FastAPI routers / schemas / error boundary
        ↓
services / runtime orchestration
        ↓
repositories / SQLAlchemy models / db
        ↓
PostgreSQL
```

静态 extension registry 作为组合根向 API、runtime tool 和 provider 贡献能力；服务通过明确的 provider/tool 接口使用扩展，不反向让扩展依赖页面。parser/compiler 负责 package artifact 的边界，scheduler 负责队列与生命周期，不把执行细节放入 API router。前端 shared components 不拥有 route、API 或 domain state。

## 接口与安全边界

- `/health` 仅表示进程存活；`/ready` 还要求数据库可连接。
- 设置 `SIGNALDECK_API_TOKEN` 时，除 `/health`、`/ready` 和 `OPTIONS` 外的请求需要 `Authorization: Bearer <token>`；本地默认配置可以不设置 token。
- `AGENT_PLATFORM_ENCRYPTION_KEY` 加密 Model Connection API key 和 package secret。读取、导出、run detail、日志、诊断和 metadata 不返回原始 secret。
- Workflow Package schema 默认 closed；禁止 `additionalProperties`、`allowAdditionalProperties` 和 `patternProperties`。secret reference 只进入 HTTP request 字段。
- HTTP operation 默认仅允许 `GET`、`POST`，默认拒绝不安全 HTTP、私有网络和重定向，并限制超时、请求/响应大小；配置改变这些边界时必须按受影响风险验证。
- MCP runtime 默认关闭，stdio command 使用允许列表；MCP 的 env、headers、query 属于 secret-bearing runtime config。
- package provenance、export 和 error details 只暴露安全的 identity、结构和经过过滤的值，不暴露数据库 id、原始凭据或内部堆栈。

## 本地与拆分部署模型

本地启动由 `start.sh` 调用根 `docker-compose.yml`：`db` 提供 PostgreSQL/pgvector，`app` 在单个容器内运行 Nginx、FastAPI 和 scheduler；宿主机默认只发布应用端口。

拆分部署使用 backend image、单独 scheduler role 和 frontend image。frontend Nginx 将同源 `/api` 请求代理到 backend；scheduler 不提供 HTTP 面，只从数据库领取并执行 queued run。多个 scheduler replica 可以通过 advisory lock 安全竞争，但当前个人本地部署不以高可用为目标。

## 质量属性与已知限制

- **可复现性**：运行使用 immutable package snapshot；compiler section 排序、canonical JSON hash 和 export redaction 必须确定。
- **可观察性**：Run、step、agent invocation、HTTP operation、queue/progress、retry/failure 和最终输出均有持久化 projection；可选 Logfire trace/span id 不应成为运行正确性的前提。
- **数据完整性**：启动用 `create_all`、preset seed 和 stale-run recovery，没有迁移框架；schema 变更需要重建数据库。运行保留默认关闭，设置 `SIGNALDECK_RUN_RETENTION_DAYS` 后仅清理终态旧运行。
- **依赖限制**：FastAPI 当前保持 `>=0.136.3,<0.137`，直到 Logfire 的 OpenTelemetry 依赖允许 `opentelemetry-sdk>=1.43` 且 instrumentation 达到 `>=0.64b0`；原因和解锁命令见 [`handover-deps-follow-up.md`](handover-deps-follow-up.md)。
- **边界风险**：外部 provider、网络请求和 MCP server 的可用性不由 SignalDeck 保证；本地内网便利性不能转化为公网、生产容量或多用户安全承诺。

## 当前架构例外

本地模式允许使用默认开发 encryption key 和不配置 API token，以减少个人调试的启动成本；生产 runtime mode 会拒绝默认数据库 URL 或 placeholder encryption key，并记录未配置 API token 的警告。该例外仅适用于本地/开发边界，补偿控制是现有 secret redaction、HTTP/MCP 限制、单用户内网部署假设和适用质量检查；当部署公开或进入生产时必须重新评估并使用显式凭据与认证边界。
